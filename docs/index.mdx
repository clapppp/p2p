## 무엇인가요

**PeerCon**은 **외부 의존성 없이** 순수 **Java JDK**만으로 만든 P2P 데스크톱 화면 공유 프로그램입니다.
Netty를 공부하다가, 추상화 레이어 없이 **Java NIO**로 저수준 네트워킹을 직접 해보고 싶어서 시작했습니다.
**UDP 홀 펀칭**과 **논블로킹 I/O** 같은 핵심 메커니즘을 이해하는 것이 목표였습니다.

Java 데스크톱 앱이라 이 페이지에서 바로 실행할 수는 없습니다. 대신 구조와 배운 점을 정리했습니다.

## 아키텍처

![PeerCon 아키텍처](/projects/peercon/peercon_architecture.png)

- **서버**는 셀렉터(Selector)와 워커 스레드 구조로 요청을 처리합니다. 접속한 피어의 공인/사설 주소를 기록하고, 서로의 주소를 알려 주는 STUN 비슷한 역할을 합니다.
- **클라이언트**는 요청량이 많지 않아서 블로킹 채널을 사용합니다.
- 서버를 통해 서로의 주소를 교환하고 **UDP 홀 펀칭**으로 직접 연결이 만들어지면, 화면을 캡처해 압축한 프레임을 피어끼리 직접 주고받습니다.

## 연결이 만들어지는 과정

1. 두 피어가 서버에 TCP로 접속해 자신의 주소(공인 IP·포트, 사설 IP·포트)를 등록합니다.
2. 서버가 상대 피어의 주소를 각자에게 알려 줍니다.
3. 두 피어가 **동시에** 서로의 주소로 UDP 패킷을 보냅니다. 각자의 NAT에 "상대에게 나간 기록"이 생겨서 상대의 패킷이 통과합니다.
4. 같은 공인 IP 아래에 있는 피어끼리는 사설 IP로 직접 통신합니다.
5. 연결이 되면 `Robot`으로 캡처한 화면을 압축해 UDP로 전송합니다.

## 배운 점

**서버**
- P2P 직접 통신에서 STUN 서버와 TURN 서버의 역할을 이해했습니다.
- 블로킹 I/O를 언제 쓰는지, 소켓이 여러 개일 때 논블로킹 I/O와 셀렉터가 왜 필요한지 배웠습니다.
- 대칭형 NAT 환경에서는 홀 펀칭이 안 되고, 그때 TURN 서버가 필요하다는 한계를 확인했습니다.
- 커스텀 프로토콜을 설계하고 바이트를 직접 다뤘습니다.

**클라이언트**
- `java.awt.Robot`으로 화면을 캡처하고 압축했습니다.
- NAT 홀 펀칭으로 직접 통신을 구현하고, 대칭형 NAT에서 생기는 문제를 분석했습니다.
- 피어들이 같은 공인 IP 아래 있으면 사설 IP 통신이 필요한 이유를 이해했습니다.

## 실행 방법

[GitHub Releases](https://github.com/clapppp/peercon/releases/latest)에서 `client-1.0.jar`를 받아 실행합니다. (JDK 설치 필요)

```bash
java -jar client-1.0.jar
```

직접 빌드하려면 레포를 clone한 뒤 `p2p-client`에서 `mvn package`를 실행하면 `target/`에 jar가 만들어집니다.

시연 영상(GIF)은 용량이 커서 [GitHub 레포](https://github.com/clapppp/peercon)에서 볼 수 있습니다.
